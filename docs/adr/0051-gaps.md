# 0051. Gaps around tiled windows and a floating bar

Date: 2026-10-17

## Status

Proposed. The user asked for a gaps mode on the Appearance page. With it on, the bar floats off
the screen's edge with rounded corners, and the same configurable gap applies to tiled windows.
Where the setting lives and how the parts share it are my design.

## Context

Tiled windows (ADR-0014, ADR-0049) fill the work area edge to edge, and the bar
sits flush against the screen's edge. Tiling window managers (i3-gaps, Hyprland, Sway) leave a
gap around and between windows, and many people prefer that look, with a bar that floats too.

Three programs need the setting:

- **The compositor** places tiled and maximised windows.
- **The bar** has to float and round its corners.
- **Settings** needs to change it.

The bar's config holds what the whole shell wears (skin, wallpaper). The compositor's config
holds what the compositor does, and the compositor already re-reads it within a second of a
save (ADR-0039).

Layer shell already has a way to float a bar: a layer surface's margin. The compositor adds the
margin on an edge to that surface's exclusive zone (Smithay's layer map does), so the work area
ends past the floating bar with no extra code.

## Decision

- **One place: `[gaps]` in the compositor's config**, with `enabled` (off by default), `size` (8)
  and `radius` (8), each up to 64 logical pixels. The gap is mostly about tiling, so the
  compositor owns it. The bar reads the same table rather than keeping a copy that could drift.
- **The compositor** tiles in `tiling_area`: the work area less the gap all round, and the gap
  is capped so a small screen keeps most of its room. `rect_for` leaves the gap between the
  halves. A change of gap re-places the placed windows. (Maximising and the tiled states
  changed in ADR-0052: maximised windows ignore the gaps, and windows in the gaps aren't
  tiled on any side.)
- **D-Bus tilers** (ADR-0049) get the tiling area from `WorkArea()`, and the gap between windows
  from a new `Gap()`. `WorkAreaChanged` follows a change of gap. The thirds example leaves gaps.
- **The bar** checks the compositor's config each second, along with its own. With gaps on, it
  sets a layer-shell margin of the gap on its edge and both sides (patina-shell's
  `Host::set_margin`), and draws rounded corners with an outline all round instead of the line
  along one edge. Menus that open from the bar already keep clear of its exclusive zone, so they
  open above the floating bar.
- **Settings' Appearance page** has a Gaps section: a checkbox, and sliders for the gap and the
  bar's corners. It writes `[gaps]` with `toml_edit`, keeping the rest of the file, and saves
  when a slider is let go.

## Consequences

- One switch changes the whole look, and the compositor and bar can't disagree.
- With gaps on, the bar is no longer at the very edge of the screen, so throwing the pointer at
  the edge no longer reaches it.
- Windows don't get rounded corners from the compositor. Patina apps draw their own frames, and
  rounding other apps' windows would need the compositor to clip them as it draws.
- The bar now reads the compositor's config. If the compositor's config moves or changes
  format, `bar/src/gaps.rs` has to follow.
